# Re-audit: core bf4225663068 custom-endpoint pool origin binding (fork main a3fe7bf2c7ab)

Card t_01a1d874f17bda10. Upstream bf4225663068 ("bind every pooled custom-endpoint key to the origin it was
entered for", merged into fork main by 4ab8a82a979b) moved two pinned files.

Drifted pins (old digests kept, new added):
- `execution-compatibility.json` `agent/chat_completion_helpers.py`: aad5d772aa60 -> a436b8ec5e5e
- `execution-compatibility.json` `agent/agent_runtime_helpers.py`: 94780fab321c -> 72ee74c4a20b

What changed (+2/-2 in each file): `_rebind_fallback_credential_pool` (fallback activation) and
`_swap_switch_runtime` (`switch_model`) now attach `custom_entry_pool.load_route_pool(provider, base_url)`
instead of `credential_pool.load_pool(provider)`. For a built-in identity that is the same `load_pool`; for a
custom entry's identity, including a `providers:` entry named like a built-in (`providers.anthropic` on a
proxy), it is the entry's origin-bound view (`entry_scoped_pool`): a row is kept only if the entry re-seeds it
or its recorded address (for an unrecorded row in a built-in's pool: the built-in's own host) is on the
target origin.

Against selection.py's seams:
- Client factories, `recover_with_credential_pool`, `_failed_credential_identity`, `interruptible_*_api_call`,
  `perform_api_call`: untouched. `switch_model`: only the pool it attaches changed; `route_wrapper` still
  compares provider/model/base_url before and after and drops the pick on any route change.
- New fence: yes. `read_snapshot`/`choose_snapshot` read raw persisted rows, and `choose_snapshot` treated a row
  with no recorded `base_url` as serving the current route. On a custom entry that shadows `anthropic` or
  `openai-codex`, a manual pick could therefore send a built-in account's key to the entry's host, which core
  now refuses. Fix: `reject_custom_entry_route` refuses any route `custom_entry_pool.is_custom_runtime`
  classes as a custom entry's (fails closed on an error; no-op on cores without the module). Built-in routes
  are unchanged. RED/GREEN: `tests/test_selection.py::CustomEntryOriginFence` (fails with the call removed).
- selection.py changed, so the recovery composition was re-checked: `recovery_wrapper` is byte-identical and
  its `choose_snapshot` call can only gain a `SelectionRejected` for a custom route, which it already maps to
  `(False, has_retried_429)` (normal recovery). `fast-rate-limit-fallback/account-usage-compatibility.json`
  refreshed to the new selection.py digest.
