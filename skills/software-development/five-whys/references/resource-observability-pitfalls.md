# Resource observability pitfalls

Reference for skill `five-whys`: its SKILL.md links this file from the step that needs it.

## Historical interruption and fleet audits

- Preserve the original measurement interval and activation evidence when expanding coverage; a later clean window cannot repair an earlier failed numeric gate. Derive interruption predicates from pinned and installed event writers, including checkpoint/result pairs that can continue the same run without a reclaim. Correlate stable event and run identities; count a checkpoint and its corroborating result once, and keep unknown causation separate from confirmed updater activity.
- Reconcile worker names against instance IDs, launch/termination API events and boot identities before excluding retired nodes. Compare valid UUID representations semantically while retaining both raw forms. A successful termination request plus later absence is not a fresh terminated-state response, and retirement after the measurement window does not remove historical exposure.
- Enumerate local boards, profile boards, replicas and registered resource paths, validating the actual registration format before decoding it. A registry may contain JSON strings rather than objects. Preserve malformed/missing records and missing stable IDs as coverage gaps; current sync timestamps and empty snapshots do not establish historical completeness or zero hold-minutes.
- Transfer large remote evidence through bounded chunks with a declared byte length and content hash, not a successful command's possibly truncated stdout. Verify the complete decoded artifact before aggregation and retain transport failures separately. Exercise real registration samples and query boundary controls alongside synthetic positive/negative cases.

## CPU acceptance from nested counters

Before spending a bounded live capture, trace the acceptance metric to the counter's entry/exit code and inventory its child counters. Verify what is included, when cumulative values publish, and whether the snapshot carries process/start identity and deployed-code provenance; a valid same-PID interval alone does not establish the metric's scope.

For saved evidence, recompute cumulative deltas and percentages in code, then reconcile them to the reported result. Treat nested `thread_time()` scopes as inclusive unless the implementation explicitly subtracts children: thread-level deduplication does not make each named scope exclusive. Do not add child CPU to its enclosing total or call the remainder local-only when it still mixes local work and transport processing. Synchronous HTTP/TLS/serialization consumes thread CPU; neither network wall wait nor a historical network percentage measures that exclusion.

When the measured total exceeds a local-only budget but the identifiable local subset does not, check whether the unpartitioned remainder can decide the threshold. If not, report acceptance as undetermined, not failed or passed. Counters committed on scope exit also have in-flight snapshot-boundary uncertainty. A source-and-snapshot review can establish this limitation without another capture; repeating the same counters cannot recover a missing partition.

## Pitfalls

- For update-admission reservations, distinguish a logged `tui turn finished` from physical worker completion. The turn worker retains custody through outcome refresh and post-turn housekeeping; nonblocking stacks can show `prompt_turn.run_body -> refresh_turn_outcome` performing process-result ownership scans or waiting on remote-card links after the bookend. Correlate reservation IDs/generations with those stacks and natural disappearance before declaring a leak. Separately preserve `turn opted out of auto-continue` as a legitimate refusal. A strict pause timeout naming only an aggregate reservation count does not identify the historical holder; do not infer it from later generations. If nonblocking dump loses a changing frame, a bounded low-rate `record --nonblocking --idle` can collect usable stacks without suspending the backend.

- For a bounded macOS CPU-recurrence collector, validate cumulative CPU parsing against native `ps -o lstart= -o time= -o comm=` on a disposable process before enabling: Darwin emits minutes:seconds.hundredths (for example `0:00.00`), not necessarily hours:minutes:seconds. Keep native sampling/output-limit qualification separate from Linux mocks; an owned-child timeout is failed qualification, not evidence that the observed app froze. Require independent approval of the actual collector, fixed single-use custody, absolute expiry, attempt/storage bounds and private stacks before activation.

- Before classifying a loopback capture as encrypted, probe the exact listener with HTTP and HTTPS controls. An SSH-tunneled connection is encrypted on the network leg, not necessarily on the backend's loopback listener. Parse requests and responses by TCP stream with sequence reassembly, deduplication, body framing and gap/completeness accounting; aggregate only path/count/byte metadata, not auth headers or private bodies. If tcpdump cannot create a file under a home directory even after `-Z`, use an approved capture path (AppArmor can constrain writes independently of Unix ownership), then remove private raw bytes after producing the sanitized aggregate. A dominant byte share identifies a producer to investigate; it does not establish capacity exhaustion without a measured transport budget.

- Before predicting an unnamed (residual) CPU share, split it per thread. One never-ending work item, such as a loop submitted once to a pool, can carry nearly all of it, and scopes that book CPU only when an item exits can never name it. Give each iteration its own outermost pass, or book the CPU of open scopes at snapshot time.
- On macOS, every `subprocess.run` from a ~1.7 GB, ~120-thread Python process costs ~42 ms of the calling thread's CPU; from a small process it costs ~1.5 ms, and an absolute executable path does not help. A probe that spawns on every loop round is therefore a CPU sink, and tests that stub the probe never show it: measure spawns per round in the real process.
- For macOS CPU attribution without suspending a Python gateway, use libproc cumulative per-thread user+system nanosecond deltas across the measurement window, not `sample` occupancy. `proc_pidinfo(pid, PROC_PIDLISTTHREADS=6, ...)` yields pthread handles consumed by `PROC_PIDTHREADINFO=5`; `sample` reports different native IDs. Query those native IDs with `PROC_PIDTHREADID64INFO=15` (same `proc_threadinfo` struct) and match cumulative counters to establish the crosswalk, especially when thread names repeat. A named executor's CPU is not automatically its sampled caller's CPU: native SSL polling is waiting, and Python caller identity may remain unknown. Pthread handles can be reused when short-lived pool threads exit: negative cumulative deltas prove identity changed, and clamping them to zero cannot recover exited-thread CPU. Use process-level CPU deltas for the acceptance total; treat per-handle measurements as attribution only unless native identity is stable across both endpoints. Preserve live-turn/worker checks with the window and label contaminated measurements, even if the total is low. A durable `tui` session lease can mean an attached chat, not an active turn: corroborate actual turn/writer activity rather than treating every unexpired lease as busy. When replaying a cached reader against isolated live-data copies, preserve its real config inputs and runtime TLS installation; a missing config file can disable caching and manufacture deepcopy/expansion costs, while an uninitialized truststore omits production certificate-verification work. Use thread CPU time for cProfile's timer when attributing CPU, not its default wall clock.
- For worker-node observability, do not derive process evidence only while iterating primary task rows: pickup/eviction can separate execution from row retention. Bind exact worker-client argv plus task/board/database identity independently, using the database home's profile rather than the assignee profile. Bound pickup-log grace by event time and require a unique board match; never treat absent rows as closure. Recheck stale promotion diagnoses against the live store and test a live-worker snapshot with its primary row removed.
- **Before profiling a live service, rule out observer-induced stalls.** Use `py-spy record/top --nonblocking` for attached production targets, with a bounded duration. Default ptrace sampling can suspend threads long enough to create the timeout being investigated; a requested duration is not a bound when sampling falls behind. Correlate profiler start/end and lag warnings with server loop coverage gaps and client failures, and discard those intervals as ordinary-load evidence. Never reproduce blocking attachment against the user's live backend; use a separate fixture. The coach profiler-safety pre-tool guard enforces common command forms, not dynamically generated scripts; on the hub and MacBook `~/.local/bin/py-spy` is a wrapper (hermes-mods `tools/process-safety/py_spy_nonblocking.py`) that adds `--nonblocking` to every attached record/top/dump, so check `ls -l ~/.local/bin/py-spy` still points there before profiling another host. When a backend stalls, grep the host's `journalctl` for `COMMAND=.*py-spy` in the window before blaming load.
