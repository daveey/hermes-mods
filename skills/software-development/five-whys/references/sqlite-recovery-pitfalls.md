# SQLite recovery pitfalls

Reference for skill `five-whys`: its SKILL.md links this file from the step that needs it.

## Pitfalls

- Do not infer an uncheckpointed WAL or a permanently pinning reader from WAL file length alone: the file can retain its allocation while checkpoint backfill advances. Where file-only inspection is authorized, a separate short-lived process can read the native WAL-index header/backfill/readmarks and correlate active SHM read-lock slots with `/proc/locks`; never open/close SHM behind a process's live SQLite connections. Treat this as non-atomic, validate duplicate headers and WAL generation, and do not attribute a stale readmark without its corresponding active lock. Moving backfill/readmarks disprove a continuously fixed pin during those observations, not intermittent pins or the original historical cause. Preserve the file-size acceptance independently, even when checkpoints demonstrably progress.

- For shared payload interning, hydrate a receipt and its blob in one SQLite statement or a caller-owned transaction. Reusing an autocommit pooled connection for two SELECTs does not establish one snapshot: replacing the receipt and retiring its last blob between fetches can break hydration. Test this with a real WAL writer interleaving after row fetch. Recovery/salvage can independently omit receipt, blob and per-owner reference rows; rebuild reference custody from validated surviving receipts before last-reference GC trusts it, and fail closed on missing/corrupt payloads. Exercise the actual recovery entry point and its CLI, not merely a SQL copy: a codec's typed ValueError subclass can fail closed yet escape a CLI that catches only recovery-specific errors. Translate at the recovery boundary, preserve rollback and source bytes, and test strict/partial mixed malformed legacy custody as well as missing/corrupt blobs. Keep old in-memory readers fenced from ref-only writes until a readers-first rollout and inline rollback are verified.

- Before attributing `read pool at capacity (8)` to eight active readers or long writes, trace every admission gate behind the warning: per-file permits, process-wide permits and FD headroom can share one message. Read the actual service process's RLIMIT_NOFILE, not the inspector shell's. Inventory result retention by `settled_at`, not session age; a newly introduced settlement timestamp can leave zero rows past a seven-day retry horizon even when sessions are older. A static retention exemption or escaped-cursor fixture is a mechanism risk, not proof it explains current disk bytes or historical WAL growth.

- For large live SQLite size inventories, query `dbstat` one object at a time with `WHERE aggregate=TRUE AND name=?`, enumerate `sqlite_master` tables and indexes, and bound each inspector in a subprocess. A full `GROUP BY name` scan, or a `name NOT IN (...)` filter, may traverse the whole store before returning; a progress-handler deadline need not interrupt work inside a virtual-table scan. An SSH/tool timeout can leave its remote query alive: verify and terminate only the owned inspector, then use a genuinely narrower query. Close each connection promptly so the diagnostic does not itself pin WAL. Keep virtual FTS parents (no physical pages) separate from their shadow tables, and label per-object observations as non-atomic rather than a transaction-consistent size cut.

- For `attempt to write a readonly database` from a SELECT, capture the extended SQLite error code/name before classifying it as permissions or quota. A real killed rollback-mode writer that spills dirty pages leaves a hot journal; a mode=ro consumer then raises SQLITE_READONLY_ROLLBACK (776) until SQLite can recover. Reproduce in a disposable database using a pipe handshake after a real spill, kill/reap only that owned writer, and invoke the actual installed consumer. Test that recovery preserves the committed active brake and original payload, rejects application writes, cannot create a missing database, and keeps the original deadline. A narrow existing-only mode=rw plus query_only fallback may permit SQLite recovery; unrelated/unknown codes and failed recovery must remain fail-closed. A later successful ordinary read does not prove the historical error's code or fix, and a recovery connection can legitimately repair journal/database bytes without changing committed ledger rows; do not describe it as physically write-free.

- For a consistent backup of a busy WAL database, explicitly begin a read transaction and establish its snapshot before `Connection.backup`; otherwise external writes can repeatedly restart the backup and prevent completion. Run one bounded, low-priority producer with a wall-clock deadline, restrictive umask and an owner-scoped durable output directory. Do not claim a partial destination is a snapshot or run integrity against it; close the completed destination and reopen it immutable/read-only first.

- For repeated SQLite corruption in a process with live connections, search fresh Git history for an already-landed fix before attributing the incident to a vulnerable SQLite version or a nearby backup/update. Plain `open()/close()` of the database **or `-shm`** in that same process can cancel its POSIX SQLite locks, even when the read is nominally read-only; a helper parameter can hide that path from a literal-path scanner. Reproduce with a held `BEGIN IMMEDIATE`, invoke the real header/signature reader, and require a foreign process to remain locked out. Route reads through the existing lock-safe cached-descriptor helper and test same-file helper propagation in the static scanner. Distinguish a reproduced lock-loss mechanism from historical process attribution; use retained audit/lock observations for the latter.

- For database-size exhaustion, verify reads and writes separately: a healthy `/health` or empty change-feed GET at an unchanged head can coexist with rejected operation and lease writes. When diagnosing a full replicated Board database, record the feed head/cursor alongside the failing write response, and distinguish restored reads from recovered sync or admission. Verify Board recovery through a supported successful write, advancing authoritative head, replica convergence and normal queued-work admission. For an incident diagnostic preflight, test both failing reads and readable-but-full state; requiring every read to return the write-path error can prevent diagnosis of the very outage being investigated. Pin any incident-specific alternative to the observed service revision and frozen head, with regression tests and independent review.

- When a SQLite header contains a TLS-shaped record, preserve the complete file and sidecars before testing a header-only reconstruction on an offline copy. Bound attribution: the bytes suggest a non-SQLite write, but do not identify its process or prove descriptor reuse. Derive page size/count and counters from surviving structure, require full integrity and foreign-key checks, verify every byte outside the damaged header is unchanged, and reconcile every table including operation/decision receipts before and after a guarded swap. Do not regenerate approvals from transcripts. Report recovery loss separately from writes rejected during the outage; a valid repaired file cannot prove those writes succeeded. Exercise the actual hook and authenticated queue; a deliberately deleted probe session should remain absent, not be recreated merely to turn its 404 into 200.

- For SQLite poll stalls, inspect transaction mode even when the SQL is SELECT-only. In rollback-journal mode, `BEGIN IMMEDIATE` followed by a no-op commit still requests an exclusive lock; an existing shared reader can strand it at commit and block new readers at their first PRAGMA/schema access. Reproduce with a held shared transaction on an isolated database. Move purely read-only methods to a query-only deferred snapshot, preserve immediate/FULL-sync mutation transactions, and test populated decoding plus connection cleanup. Do not identify the initial long-lived lock holder from this contention pattern alone.
- Recovering a damaged SQLite database by hand as the symptom fix. Several agents chasing the same alert
  each swap a rebuilt copy in, and every `mv` or sidecar `rm` under open WAL connections corrupts the next
  copy. For a Kanban board, the symptom fix is `hermes kanban [--board <slug>]
  recover` (single-owner lock; a second run names the holder's card, so comment there), proven by
  `sqlite3 -readonly <db> 'pragma integrity_check'` = `ok` plus its loss report. Other databases: the
  sqlite-live-guard `swap_db.py` helper. Never hand-run dump/`.recover` then `mv`.
