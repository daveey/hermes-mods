# Runtime integrity pitfalls

Reference for skill `five-whys`: its SKILL.md links this file from the step that needs it.

## Pitfalls

- For evidence verifiers whose callers skip `ValueError`, separate invalid evidence from dependency unavailability before sanitizing exceptions. A missing CAS blob behind a retained contradictory authenticated receipt must abort finalization, not remove that receipt from the conflict scan. Exercise outage on only the conflicting receipt, verify no verdict is written, restore storage, and require conflict refusal. Preserve typed operational failures across RPC and raise sanitized exceptions outside handlers when exception context itself can expose data. Align RPC raw-byte capacity with the upstream retention cap: a receipt retained before validation must remain transportable even if binary or escape-heavy, or malformed audit evidence can permanently wedge finalization.

- For raw protocol frames leaking into diagnostic logs, enforce channel ownership at the shared output sink, not only the final routing fallback. Session records, bound contexts, and lifecycle callbacks can retain the same stdio transport and write directly. Test absent, session-bound, and context-bound routes plus real tool-completion callbacks; include positive explicit-client delivery and ordinary error logging controls. A global-broadcast-only guard does not protect session events or responses. Audit retained logs on-host and emit counts/types only, never matching credential values; zero pattern/exact-known-key hits is bounded detection, not proof of absence.

- For journal OOM detectors, distinguish `oom_memcg` (the constrained cgroup) from `task_memcg` (the victim): suppress typed worker-local failures only for the former, never global or parent-cgroup pressure. Persist partial task dumps and a delivery outbox across cursor advances, and test closed-target retries and timestamp-recovery replay after archive. Sample MemAvailable after the journal read for the post-event value; label the prior poll's timestamp rather than implying kill-time telemetry. Run Hermes tool handlers through `hermes_cli._launchers.runtime_command(..., code=...)` so systemd uses the managed SQLite/dependencies, not the system Python's potentially old SQLite. A daemon-created probe card is outside a worker's archive authority unless creation provenance explicitly binds it; arrange supervisor cleanup before the live probe.

- For SQLite WAL reader caches, DB/WAL stat equality is not a commit-visibility key: frames can be written and fsynced before the SHM index publishes them. A stat/read/stat bracket can therefore cache old data under the new stamp indefinitely. Use `PRAGMA data_version` on a retained read-only autocommit connection, include connection generation and file identity, bound/close observers, and bracket expensive reads with that key. Test a real separate writer plus the WAL-publication gap; ordinary commit-then-poll tests miss it. Preserve time/liveness-based decisions outside the cached data, and retain per-row decode entries across same-file concurrent commits when their sequence keys remain valid.

- For isolated SQLite replacement fixtures, close and checkpoint the replacement connection before moving its main file: `with sqlite3.connect(...)` commits but does not close, so its latest generation may still reside in the unmoved WAL. Assert the replacement preserves the intended generation as well as invalidating file identity; a fallback signature alone can make a broken fixture appear to pass. Never perform this file-only replacement on a live store.

- For sandbox scratch cleanup, distinguish monitor exit from namespace quiescence: a bwrap monitor can return while namespace init and a daemonized writer are still alive. Use a dedicated credential-free subreaper supervisor to kill/reap adopted descendants through ECHILD and acknowledge quiescence over a private pipe before removing scratch; retain scratch if acknowledgment is missing. Avoid making an imported caller process a global subreaper. Prove ordering with real non-root bwrap and a setsid/double-fork writer gated at remove_tree entry, asserting both no live sandbox process at entry and no later writes; eventual disappearance alone misses the invariant. Record RED on the unchanged baseline and GREEN on a capable runner, separately from optional isolation skips.

- For a protected-branch merge incident, recover the exact transcript command before inferring an explicit override from the admin actor. Ordinary `gh pr merge` can land red when server admin enforcement is disabled. Test the invariant across ordinary and override merge paths; a test asserting ordinary merges are unchecked encodes the trust gap. Prefer server-side enforcement as the non-client-dependent barrier, with hook checks as defense in depth. Verify live hook discovery and a read-only replay of the historical failing head; do not risk a red merge into production merely to prove rejection.
