# Declared loader metadata versus runtime closure

When standalone Darwin system libraries return ENOENT, inspect the already-installed `dyld_info` usage before assuming cache tooling is absent. Its `-uuid -linked_dylibs -platform <exact paths>` can report cache-backed images; aliases may return the same UUID/dependencies, which does not prove distinct image identity.

Use `-all_dir <already inventoried root>` for extensionless-image discovery, but distinguish static archive members: retain architecture separately, map `archive.a(member.o)` to its backing archive pin, and never count archive objects or foreign-architecture slices as loaded libraries. Do not broaden discovery to unrelated installations.

Preserve full output; recover truncated metadata through one exclusive diagnostic gzip and verify the complete downloaded bytes. Utility metadata is not fresh file-hash binding, atomic capture, recursive shared-cache closure or observed imports. Keep per-executable/inherited-rpath candidates unresolved until their contexts are established. An offline extractor may accept incomplete sections; complete transport plus inventory coverage, not parser success alone, supports a complete snapshot claim.

A pinned source hash and matching cached module `__file__` do not authenticate the module's executed bytes. Branch fresh exact-byte execution from unresolved cache reuse. Classify source constants naming a file separately from an actual consumer read; declarations do not create runtime read edges.

For a dedicated-process source bootstrap, capture/hash ordinary local modules before importing them, execute retained buffers without a bytecode loader, and reject preexisting reserved names without replacing them. Preload lazy local consumers before issuing a provenance receipt, then check their module-object identity at the owner boundary. Keep generic fixture-pin receipts distinct from qualification against the in-source production pin set; self-consistent caller pins alone do not identify the approved assembly. Exercise a real matching-size/mtime stale pyc, custom pins, late reserved-module replacement and the actual fresh isolated assembly import, not only extracted loader fixtures. This does not authenticate earlier interpreter/stdlib/native startup or resist malicious in-process state mutation.

Do not silently insert a sandbox wrapper into an initial-exec-only custody contract: wrapper-to-runtime exec is a different generation. First evaluate confinement inherited from the already dedicated guardian as a no-wrapper candidate, explicitly declaring any shared union of role rights. Neither design proves OS denial or Electron/helper compatibility; a generic Python audit callback, documentation search excerpt or mock API call cannot grant native admission.

For a ctypes sandbox error buffer with unknown allocation length, never use fixed-size `string_at(pointer, cap)`: the cap can read beyond the NUL-terminated allocation. Keep the original opaque pointer, emit only a fixed bounded category and free it through the documented API. Declarative image/cache/helper/FD fields are not verification; preserve unconditional whole-owner refusal until executable native qualification exists. A compact subtree policy can reduce a large inventory to practical text but grants future descendants and listing rights, not exact snapshot custody or least privilege. Require a real existing canonical renderer scratch generation in the same pre-either-launch path receipt, then bind that exact consumer into policy generation. A source-reviewed ABI candidate and successful fresh isolated import do not qualify native denial/inheritance or Chromium's second installation; those need a separately reviewed bounded disposable-child harness before any native call.
