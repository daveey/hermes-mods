# Collector and panel verification

- Verify the exact watch definition on the collecting gateway before changing instrumentation. A chat machine's local registry can be unrelated.
- Distinguish a fixture collector/API integration test from a real canonical submission, a running collector cycle and a rendered Desktop panel. Report each proof separately; passing HTTP fixtures does not prove production rollout.
- For same-user, headless HTTP readback on a native gateway, use its supported private control socket: resolve `$HERMES_HOME/gateway.sock.path` (fallback `gateway.sock`), send newline-delimited `{protocol:1,id:1,verb:"identify",params:{}}`, then request `session-ticket` with that descriptor's `instance_id`, the absolute home as `profile_id` and `purpose:"native-http"`. Read the plugin endpoint from the returned `api_origin` with `X-Hermes-Gateway-Ticket`. Tickets stay in-process and never enter stdout, command arguments, evidence or source control. Honor any scope refusal; do not change authentication settings.
- Read both `/api/plugins/latency/v1/series?metric=<id>` and `/api/plugins/latency/v1/ledger`. A watch with no real observations must retain `n=0`, null percentiles and its collecting label; do not POST fixture spans into production to make it nonempty.
- For pool-to-gateway readback, transfer a nonsecret, task-scoped script through the supported administrative transport rather than piping into a wrapper that may discard stdin. Retain only identifier/statistic outputs, not raw unrelated source rows or full endpoint bodies.
- Keep request/card correlation independent of nearest timestamps. Canonical operation IDs, owner routes, server-owned bindings and committed receipts establish identity; source timestamp precision and missing joins must be disclosed rather than repaired with invented timing.
