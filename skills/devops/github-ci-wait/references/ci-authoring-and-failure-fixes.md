# Writing CI, and known CI failure classes

Read when adding a script, test or workflow to a repo's CI, or when a CI failure matches a class below. Waiting on
CI itself is SKILL.md.

## Adding scripts, tests or workflows

- **Where a new tool goes.** Before choosing a directory for a new tool, read the CI workflows' `on.push.paths` and any plan step's path rules. A script under a shared or product directory (e.g. `shared/`, `lib/`) can trigger a full rebuild and release of every product on push. Put agent tooling where no release workflow watches (often `tools/`), and confirm by checking that no new run started after the push.
- **Path filter for a guard workflow** (scan guards, lint gates: anything that must run whenever a file it reads changes). Write `paths:` as everything minus doc/data suffixes (a `'**'` pattern followed by `'!**/*.md'`, `'!**/*.png'`, ... exclusions), not as a list of code suffixes and directories: extensionless launchers and scripts, and systemd units and timers, fall through a suffix list. Pin it with a test that enumerates the files each guard actually reads and asserts that every one matches the filter; prove the pin red against the old filter. Run that pin test in the guard workflow itself, with the workflow's own file inside its filter: a sibling test workflow's path filter usually doesn't include this workflow's YAML, so an edit to the filter would otherwise run its pin nowhere.
- **unittest discovery.** For tests added to a stdlib `unittest discover` directory, verify actual discovery as well as imports: installing pytest fixes an import error but does not make unittest execute function-style parametrized tests. Preserve every scenario when porting fixtures to unittest and add a collection-count regression; run the exact CI command on each Python matrix version without undeclared packages.
- **Cross-repository integration tests.** Wire every required environment path into the actual CI suite step, not only a local test command. An existing companion checkout does not export its paths automatically. Retain real-producer tests and add a workflow regression tying the export to that checkout before the test runner; verify the green branch run rather than replacing the producer with a mock or skip.
- **Timers and chained runs on a non-default branch.** GitHub fires `schedule:` and `workflow_run:` only from the workflow file on the default branch (`gh api repos/<o>/<r> --jq .default_branch`). Added to a workflow that lives only on another branch, either trigger never fires and reports nothing. Drive that branch's periodic or follow-on runs from a default-branch workflow or a hub cron, and confirm the first run actually started.
- **Shard counts.** Match full-suite shard counts to the reusable workflow's timeout envelope. Reducing an eight-shard matrix to two while retaining the same per-job timeout can cancel every Python job even when e2e is green. Keep the gate's required exact job names, workflow matrix, and test fake synchronized; never count cancelled shards as green or compensate by weakening assertions.

## Input-specific controls and source guards

1. Record exact heads, run IDs, dispatch inputs and expected named job/test outcomes before waiting. Wait with `wait_for_ci.py --run-id ID --expect ID:JOB=CONCLUSION` (SKILL.md), never a hand-written waiter: it refuses an empty manifest (`no runs to wait on`, exit 1) and fails on missing runs or jobs, so a time-filtered empty result cannot become “all done.” Preserve each attempt's log and inner exit status separately.
   When an authenticated admission wait exhausts its local request budget, reconcile exact-SHA and branch runs before renewing credentials or retrying a POST. Resume with bounded wait slices under fresh broker grants rather than one long-lived grant; a successful recovery used slices of at most 20 minutes. Reuse any accepted run instead of dispatching again: a local budget denial is not evidence that GitHub rejected or never received the submission.
2. Execute the workflow's entire plan job locally before dispatching helper controls, not just the edited shell step. Generated Python embedded in a single-quoted shell command can break on `%r` output; fixing that quoting still does not prove repository plan guards accept narrowed packages or test filters. Prefer source-only mutants with the original workflow unchanged.
3. Read completed job logs with `gh api repos/OWNER/REPO/actions/jobs/ID/logs` when whole-run logs are withheld while a sibling job is queued. For deliberate mutants, a watcher's exit 1 can be the expected result, not a failed dispatch: reconcile redirected dispatch logs and exact-SHA runs before retrying. Classify plan failure, compilation failure, skipped job and named assertion failure separately; only the last establishes behavioural RED. Require the predicted assertions and no unexpected failures. Re-run sensitivity checks after composing additional guards: a new earlier refusal can make a previously causal test pass even when its intended downstream guard is removed. Construct a fixture that reaches that downstream guard with the earlier guard satisfied, then require the single-guard mutant to fail by assertion; a combined mutant does not prove either guard independently. Report Linux source checks as Linux evidence, not native execution.
4. Give every source guard a CI owner with declared parser dependencies and fetched pre-change baselines. Include the dependency lock in triggering paths, or run the inexpensive guard job unconditionally; lock-only changes otherwise merge without testing the new environment. Missing dependencies or baseline objects must fail the authoritative job, even if another platform explicitly skips unsupported checks.
5. Prove meaningful guard execution with empty-script, print-only, early-exit, all-skipped and optimized-Python controls. Reject optimized execution when guards rely on `assert`. Count declared grammar skips separately as noncoverage; pin each allowed skip's identity/reason and reject unexpected or disappeared skips. A script's exit 0 or a unittest report with no effective tests is not coverage.
6. Test a committed forbidden change against the guard in a shallow checkout. Comparing against `git show HEAD:` compares CI to itself and accepts the same bad change. Require a full immutable commit ID and verify that the object exists; a moving-ref blacklist misses arbitrary branch names, tags and reflog expressions. Enforce this before execution and on actual git invocations, including the `:<path>` operand for `git show` and the baseline operand for `git diff`. Exercise each check independently with mutants and verify missing-baseline refusal.
7. Validate the control harness with a passing full-ID case before counting rejected-ref controls. Give synthetic repositories their own matching noncoverage declarations: copying a declaration for an untracked guard can make every negative control fail for the wrong reason. Assert the named rejection diagnostic, not just nonzero exit, and retain invalid earlier controls as excluded evidence.

## Known failure classes

- **Admission guards under a local quota transport.** Classify local refusal separately from generic API trouble before allowing dispatch: a quota shim can raise `Denied` (or a subclass) rather than an HTTP 429/403. Catch refusal during both request opening and response-body reads; return the guard's refusal status (75) without polling the same exhausted grant or attempting POST. Test refusal before admission, exhaustion mid-wait, and both send-side and response-side refusal at POST. Use a loopback HTTP server to distinguish zero connections/bytes before send from exactly one accepted POST followed by response-bookkeeping denial; disable ambient proxies in that probe. Assert zero POST attempts for pre-admission denial and no repeated POST after either submission refusal. Do not describe a POST-time `Denied` as “nothing sent”: response-side quota bookkeeping can raise after the server accepted it, so reconcile the existing run before retrying. Keep unrelated exception behavior unchanged with negative controls—matching every local exception would turn ordinary errors into quota refusals. Verify with the actual transport in an isolated exhausted-grant probe as well as injected exceptions; HTTP-only mocks miss this boundary. If refusal occurs only during the re-check after an accepted POST, reconcile that existing run rather than submitting another.

- **A job goes red on a head whose code didn't cause it (hundreds of failures across old and new test files, green on earlier heads).** Suspect a hosted-runner property before the diff: GitHub-hosted jobs land on different clouds/images, and a mount option (`noexec` on `/run` or `/tmp`), kernel or sandbox setting can differ between them. Group failures by message, read the earliest traceback of each, then reproduce the suspected property locally (e.g. `unshare -m` plus a `noexec` remount) and compare per-file failure counts with CI: matching counts are the evidence, since the old log usually never printed the property. Fix with a precondition step that prints host/kernel/mount facts, corrects the property and proves it (e.g. maps a real `.so`), without touching tests. A green rerun proves the fix only if that step's output shows the bad condition was present; a pass on a runner that was already fine proves only that the step is harmless, so report it as unproven. While a job is still running its log API returns nothing: read progress from `gh api repos/O/R/actions/jobs/ID --jq '.steps[]|[.number,.name,.status,.conclusion]|@tsv'`.

- **A setup step fails and every test step is `skipped`** (apt/DNS `Temporary failure resolving`, a toolchain download; the artifact upload then fails too with "No files were found"). No test ran, so the red says nothing about the head: `gh run rerun <id> --failed` once (same run id, next attempt), note the rerun on the owner card so its worker waits on that attempt instead of rerunning again, and require the test steps to show `success`, not `skipped`, before calling the head green.

- **Python shard-only subprocess mock failures.** Inspect unexpected commands reaching the fake before blaming timing. Patching `module.subprocess.run` mutates the shared `subprocess` module, so background threads from earlier tests can consume a call-count fake intended for a camera or other subprocess. Dispatch only the intended executable/argument shape to the fake and pass other calls to the saved original. Reproduce with a concurrent unrelated subprocess caller, then run the whole affected class; assert “no target executable call,” not “no subprocess call anywhere.”
- **JS fixtures: `listen EINVAL`, then a timeout.** Keep TMPDIR roots short (for example `/tmp/wc.XXXXXX`): nesting a `RUNNER_TEMP/workspace-checks.*` root under Vitest plus gateway control sockets can exceed AF_UNIX path limits and surface as `listen EINVAL` followed by a timeout. Exercise a real nested Unix socket, executable helper, original failure status, and cleanup through the actual workflow shell. Container `sudo` does not prove mount permission; inspect mount failure and `/dev/shm` noexec/capacity. Reconcile runner label migration before changing retired container hosts; the next real job must prove tmpfs selection and memory reserve on the serving fleet.
- **Detached core-E2E gateway leaks.** Verify `HERMES_E2E_RUN_TMP` survives `coreAppEnv` into the real `gateway ensure` daemon before blaming runner liveness: runtime-variable scrubbing must preserve the lifecycle marker. Exercise both SIGKILL → next-runner recovery and normal exit through the real fixture environment; a marked `sleep` child bypasses this boundary. Pre-fix unmarked daemons require a one-off HOME/HERMES_HOME/argv/owner-verified cleanup; their removal is not post-fix live prevention proof.
- **Hermes E2E failures on loaded runners.** Audit sandbox daemon ownership before raising timeouts. `hermes -z` and viewer `/exit` deliberately retain the shared gateway: each isolated test home must stop its own home/PID/start-time-verified gateway before closing fake provider/proxy servers. Assert viewer-only cleanup first, then full runtime cleanup; never hide arbitrary children as persistent infrastructure. A cold public model-metadata fetch can also reach OpenRouter during another provider's test: seed metadata for the fake model rather than broadening the foreign-provider egress allowlist. For recording/prebuilt TUI probes, pass the installed Node explicitly with supported `HERMES_NODE` through the hermetic child's overrides; obsolete `HERMES_SKIP_NODE_BOOTSTRAP` has no reader, and Node on PATH alone still falls through to `pm.ensure('node')`. Prove attach-only isolation by forbidding PM acquisition in a real child CLI while retaining exact handoff/lease assertions, rather than raising its timeout.
- **Docker: image pushed, then `exporting to GitHub Actions Cache` fails** (`error writing layer blob: not_found`). Keep cache exports advisory with `ignore-error=true` in each `cache-to: type=gha` option list, including release and sibling image workflows. Do not use step-level `continue-on-error`: image build/load/push failures must remain fatal. Test the parsed workflow exporter policy and verify a green main push run; a later artifact-quota warning alone does not establish why the cache backend failed.
- **gitleaks install fails with "Destination file path ... already exists" on a self-hosted runner.** Self-hosted runners keep files between jobs. `gitleaks/gitleaks-action@v2` downloads to the fixed path `os.tmpdir()/gitleaks.tmp`, so one interrupted run makes every later install fail on that runner. Fix in the workflow, not on the hosts: set `TMPDIR: ${{ runner.temp }}` in the step's `env` (emptied per job). Check every runner's failure first (`runner_name` per job) to tell a systemic cause from one dirty host.

## Batch acceptance: several PRs, one suite

When the user approves batching several PRs through ONE full suite, a constituent PR does not need its own green run.
Its acceptance is the batch's evidence, but only when all of the following hold:
- One owner card builds the batch branch from fresh `main` and merges each PR's exact head with `--no-ff`, so every
  source commit is an ancestor. That card records base sha, PR heads, integration head and tree, and run URLs in a
  manifest. Fix-ups the merged tree needs (lint, code-health) go on the batch branch as their own commits.
- Before pushing, run the repo's local lint gate (e.g. `scripts/check --base origin/main`) and focused tests. A
  ratchet that only fails on the combined diff costs a full suite otherwise.
- Every necessary workflow completed green on the exact batch head: one run per workflow, never "queued" or
  "in progress", never one job standing in for the others. A PR head or `main` that moves invalidates the
  evidence: rebuild and rerun.
- Land with one fast-forward of `main` to the tested head, after checking `git merge-base --is-ancestor
  origin/main <head>` immediately before the push. Never force-push `main`. Close each source PR only after the
  landing, with the batch PR link and main sha. Never fake check statuses on the source heads.
- Once the batch PR exists, cancel only the superseded runs of the constituent PRs. Leave runs on `main` and in
  other repos alone.
- The batch is done only when the post-landing `main` suite has completed green (`wait_for_ci.py <sha>`). Waiting
  cards get the run URLs so they don't relaunch suites. If that run fails in a test outside the batch diff and
  `main` has since fixed it, a later fully green `main` suite (every workflow) on a descendant of the landed sha
  counts; record the failed run, the fix commits and the green runs in the manifest.
