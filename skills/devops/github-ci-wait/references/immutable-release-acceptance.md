# Immutable release acceptance

Before any candidate or dependency-mirror publication, check repository release immutability. When enabled, create the release as a **draft**, upload every validated asset, read back exact names/sizes/server SHA-256 digests, and only then publish (`gh release edit TAG --draft=false --prerelease --latest=false`). Published immutable releases reject later uploads with HTTP 422, including an empty release; their tag names cannot be reused even after deletion. Preserve an accidentally empty candidate as failed evidence rather than deleting/recreating or weakening immutability. Use a new reviewed source head and distinct exact-head candidate tag; reuse original input-addressed archives only when the complete compatibility-input pattern set is unchanged, retaining original manifest source, run/artifact IDs, names and digests. New-head actual proof remains mandatory. Draft releases may return 404 from the tags endpoint; obtain their database ID via `gh release view --json databaseId` and inspect the release-ID endpoint before publication.

Before publishing a release explicitly required to be immutable, check `GET /repos/OWNER/REPO/immutable-releases`; a fixed tag, checksum manifest and no-overwrite publisher do not establish GitHub's `immutable` flag. With scoped authorization, `PUT` on that endpoint enables future release immutability. An existing mutable release can be moved to draft and republished without changing its tag or assets; compare exact asset IDs, names, sizes and digests before/after, then require `immutable=true`, `draft=false` and the intended prerelease flag. The lock is permanent for that publication even if the repository setting is later disabled. Never replace assets or move a tag to repair this gap.

References: https://docs.github.com/en/rest/repos/repos#enable-immutable-releases and https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/
