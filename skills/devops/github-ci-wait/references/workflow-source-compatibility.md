# Workflow/source compatibility

After refreshing a PR with close/reopen, verify the source job's actual synthetic merge parents and executed selector regression inventory. A newly created event can still use a pre-repair synthetic merge; a post-landing event timestamp alone does not prove that the repaired base workflow executed. Read the checkout and emitted generation outputs before claiming qualification. Check every newly added required consumer too: one generation repair does not cover later qualification tooling.


When a newer PR-event workflow invokes tooling absent from an older selected PR head, trace the source selector's immutable ancestry generation before treating downstream aggregate reds as test failures. A first-generation compatibility boundary can become stale when required tooling advances.

Version each newly introduced qualification closure with its own immutable ancestry boundary and an intermediate-generation regression. When applicability differs for older exact sources, keep producer jobs unconditional and retain strict all-needs success checks; gate only the newer closure's execution/artifact steps, report older sources explicitly NOT EXECUTED/QUALIFIED, and fail reporting on missing/invalid applicability output. Keep native component inventories, checkout identities and earlier generation gates unchanged. Test an actual intermediate tree containing the earlier feature's inputs, and make shallow-history controls include a locally available boundary object so they exercise the shallow guard rather than a missing-object error. Require hosted modern execution and paired aggregation before landing; a local classifier pass is not that proof.

Version the reviewed contract boundary with an intermediate-generation regression. Preserve exact parent binding and modern-deletion fail-closed behavior; never infer compatibility from file existence. A synthetic-merge fallback must stay explicitly integration-only and record the actual checkout, not acquire exact-head publication status. Check all required consumers share that selected SHA and read back actual source-job logs after repair. When acceptance explicitly requires exact-head execution, do not silently use the integration-only fallback: a minimal forward-port of the already-reviewed missing qualification tooling may preserve exact-head selection without routine whole-main catch-up. Verify every imported path is byte-identical to the merged source, include its Cargo feature/test registration and public evidence pins, run parser controls plus actual protected publication/native replay, obtain independent exact-new-head delta review, and require genuine new-head hosted CI. Keep test-only compatibility imports separate from production or protocol changes. Keep the original required test and independent review gates open; compatibility repair is not live publication proof.

For a `pull_request` workflow that explicitly checks out the PR head, compare the actual executed workflow with both head and base: GitHub can execute newly landed base steps against an older selected source. An ENOENT for a new required qualification script can therefore precede every product test; missing JUnit/artifacts later are downstream, not independent test failures. If the new step depends on a landed production closure rather than isolated tooling, a justified clean integration of that actual merged base can be safer than cherry-picking its source piecemeal. Preserve both workflows' gates, independently compare the merge tree and imported files against the real base, obtain exact-new-head integration review, then rebuild provenance and rerun native acceptance plus hosted CI. Do not silently substitute the synthetic merge checkout or turn this into routine BEHIND catch-up.
