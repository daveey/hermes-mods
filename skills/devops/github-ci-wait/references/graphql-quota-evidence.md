# GraphQL exhaustion: measurement and REST equivalence

- Attribute the producer before changing quota or adding sweepers. Use per-host request-minute ledgers and per-command vend reasons, then corroborate the process/caller. Request attempts are not charged GraphQL points: retries and rate-limited responses can exceed the point ceiling. Do not add command counts selected by vend-start time to totals selected by request time; preserve each window explicitly.
- Read the GraphQL bucket separately from REST core. REST `/rate_limit`'s top-level `rate`/`core` remaining is not GraphQL availability; a stale GraphQL ledger is not a fresh successful GraphQL read either. Preserve the real failure and reset evidence instead of immediately retrying a blocked ship.
- When synthesizing required-check state through REST, preserve classic protection `checks[].app_id` and ruleset `integration_id`, not just context names. Same-name success from a different app or a commit status creator cannot prove a source-bound requirement. Return unreadable when that evidence cannot be established; test missing, wrong-app, same-name status and expected-app positive/negative controls through the executable CLI boundary.
- Test display-observer backoff at dispatch as well as admission. Queue another batch while the first is active and then fail the first; pending work must not run inside its newly established cooldown. A quiet stream also needs a stable cursor transition at cooldown expiry when the delay exceeds observation TTL; TTL expiry alone strands recovery. Test both interleavings without an autonomous busy-loop.
- Keep synthetic exhausted-API regressions separate from production proof. A natural exhausted completion needs its actual fallback receipt; a healthy bucket does not exercise fallback. Never deliberately burn the shared quota to manufacture a proof.
