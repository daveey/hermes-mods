# Reconciling lane-strip counts with the session pane and global totals

Use this when the user says lane pills show blocked or running cards that he can't find, or that the pill numbers don't add up to the global totals.

## Probe the live view (on the hub; read-only)

1. The deployed plugins are symlinks: `~/.hermes/plugins/{lanes,session-panel}` -> `~/code/hermes-mods/plugins/...`. Read the code there. `~/.hermes/repos/hermes-mods` has no lanes code.
2. Load `plugins/lanes/dashboard/plugin_api.py` with importlib, run it under `~/.hermes/hermes-agent/.venv/bin/python`, and call `_lane_view(6.0, '6h', True)`. Dump the result to a scratch JSON file. The useful fields are `status` (global totals by reason), `lanes[n].strip` (blocked/running/other plus cap/in_share/over) and `cards[]` (each with `reason` and `lane`).
3. Read card rows from the fleet replica, the same source the view uses, not the local `kanban.db`: `kanban_db_connect.connect_closing()` then `kanban_worker_node.open_replica(conn)`. Pull `status`, `block_kind`, `human_request` and `task_chat_links` for each card in question.
4. To see what the user actually sees, read the Desktop renderer on the Mac. Use the inspecting-hermes-desktop-dom `rend-eval.mjs` over tailnet_exec and pass the expression positionally, as a single argument. It reads sidebar `[data-sidebar-stripe]` values and the pill `aria-label`s. Close the inspector port afterwards.

## Heading summaries and stationary hover

Reconcile a single immutable producer view against visible text, DOM `title`, and heading `aria-description`; then update that view while the pointer remains over the summary. DOM title equality alone does not certify a displayed native tooltip: Chromium can retain the previous bubble even after React updates the title attribute. Verify in owned headed Chromium/Xvfb (capture the owned display, since a page screenshot omits native UI). Key only the tooltip-owning summary span by its full string so a changed summary replaces that node; keep the heading button stable to preserve focus and independent folds. Require RED/GREEN node-lifetime and browser layout regressions, plus before/after native captures.

Treat governor counts as a histogram of emitted governor rows, not held-card counts. A sparse Python Counter omits genuine zero categories; emit explicit `on`, `off`, `at_cap`, and `unknown` buckets at the producer, where enumeration is known complete. Do not default absent governor payloads or unknown source totals to zero in the renderer. Real dispatcher→producer→renderer fixtures must compare the histogram with row states and text/title/aria, including partial source and recovery. Flow-only failure can retain independent waiting-summary counts while running/you remain unknown; whole-board summary failure must invalidate waiting as well. Preserve each failed board's reason in diagnostics rather than attributing every unavailable read to tick freshness.

## Known divergence mechanisms (check these first)

- **Two "needs you" predicates.** The lanes plugin gets its "you" reason from core `kanban_lanes_flow.classify_reason`, which fires on `human_request` OR `block_kind in (needs_input, capability)` regardless of status. The session pane (`session-panel/model.py` ask logic) paints red only when a card is linked to a session, is in blocked/triage, and has a complete human_request. Count each card under the reason that applies to it.
- **Stale `block_kind`.** A card that went blocked -> scheduled/triage can keep `needs_input`. With no human_request it is a false "you" in the lanes count and correctly not red in the pane.
- **Unlinked asks.** The sidebar section lists an ask when no visible chat paints it red. That happens when the card has no unreleased `task_chat_links` row (server `unlinked`), and also when the linked chat's stored outcome is not `status.presentation.stripe == 'stuck'` (client-side partition, `uncoveredAsks` in `desktop-plugins/lanes/plugin.js`). Headless producers (terminal, bb-dev, watchers, sweeps) now get a pinned `kanban_owner_<producer>` chat through a `created` link row only. Diagnose in this order: (1) links per card from `task_chat_links`; (2) the linked session's `outcome_json` in hub `state.db` (`kind`, `source`, `status.presentation`); (3) `hermes_cli.kanban_session_outcome_tasks.select_listed_local_task_set` membership and its `via`. Inspect the installed selector rather than assuming ownership is only `tasks.session_id`: unreleased local/profile `created` task_chat_links now participate in creator membership. A tui subscription or escalation shepherd link can still resolve as `via == 'subscribed'`, which `hermes_state_outcome._read_card_items` does not treat as that chat's decision. Stranded-park escalation may therefore create a pinned, visibly linked desk chat whose canonical outcome remains waiting while lanes still lists the ask as uncovered. Read fresh `session_outcome_tasks(..., stale_ok=False)` for the exact original creator and desk chat, preserving `via`, `retained_wait`, stale/partial flags and current request; do not blame retained_wait without observing it or convert observation subscriptions to creator custody without settling decision-owner semantics. Never release an underlying safety stop merely to clear this display. So `hermes kanban notify-subscribe` does not turn the chat red, even though `annotate_kanban_activity` then lists the card in `needs_you`. Judge the fix by the outcome stripe, not by `needs_you`. A declared idle `done` outcome on an owner chat can also mask an attached ask until the derived outcome is refreshed.
- **Board scope.** Lane counts come from the hub's default board (fleet replica) only. Other hub boards (`hermes kanban boards`) and the mini's separate BB Hermes board (`~/.bb-hermes/kanban/boards/bb/kanban.db`, its own `bb_gate`/`bb_governor` with state in `~/.bb-hermes/bb-dev/{governor-state,gate-state}.json` and `holds/*`) are not counted. When the Baby Bear board shows many ready cards and the babybear pill shows few, compare board status counts on each host. Read `holds/*` to find what is stopping BB starts. A hub `dispatch_skipped` count over 48 h shows past triggers, not cards held now.
- **Running split.** `strip.running` always sums to `status.run`. A pill that shows `in_share` and a separate `+over` makes the blue numbers look as if they don't add up.

Report the count for each mechanism with card ids. The structural fix is one shared predicate, enforced by contract and invariant tests, so that lanes `status.you` equals the pane's red count and the rendered blue numbers sum to `status.run`.
