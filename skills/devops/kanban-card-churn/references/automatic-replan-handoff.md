Put the actionable plan in the prerequisite's completion **summary**, not only metadata or an artifact: the home auto-replan applier reads latest_summary (falling back to result), then appends it to the original body and comment before resumption, preserving acceptance. Verify the installed behavior when needed; do not invoke internal DB writers yourself.

Record and read back a supported original-card comment before ending. If operator preflight reports the target is local, use kanban_comment rather than routing around custody. Distinguish that verified comment from the later automatic body append; do not claim the latter before readback. Keep original acceptance and owner mandates unchanged.

Before retaining a dependency on a multi-purpose owner, re-read its newest delivered sub-scope receipt and remaining acceptance: a repaired shipping helper can be installed while the same owner stays open for an unrelated multi-day audit. Ask the existing creator to reassess only that dependency through supported custody; do not complete the owner early, unlink foreign edges yourself or wait for its unrelated audit. Reuse the existing repair/landing owners and make the consumer wait for a landed-SHA/terminal-CI predicate rather than every acknowledgement or progress comment.

Distinguish productive continuations from repeated failed attempts before splitting work. When exact-head qualification and review are already recorded and an existing landing waiter is alive, make the replan a finite closeout checklist: recover and validate preserved evidence, follow the current candidate's exact-head CI, verify the landing receipt and main ancestry, then clean owned worktrees and attach artifacts. Do not restart completed repro/stress work or duplicate intake merely because the run-count threshold fired. A successful source-PR CI notification can wake the card while train-candidate native CI remains in progress; read both identities before classifying the wait as stalled.

For a train-wait replan, read current GitHub mergeability as well as the exact-head retained queue status: a previously clean approved head can now conflict with main while its consumed-label submission remains active. Diagnose conflicts in isolation, retain the existing queue identity, and coordinate its supported head-update/cancellation path before publishing a repaired head; fresh source approval and CI are required for a new head. Do not turn stale position or process handles into repeated observation runs.

Refresh the last checkpoint's exact native run and first failure before ordering work: a run described as in progress may now pass previously broken UI censuses and expose a later Release boundary failure. Preserve the passing named-test evidence, diagnose the new failing gate without weakening its exclusion contract, and make a portable acceptance-to-SHA/run/artifact ledger the next executor's entry point; repeated design-only investigation and stale scratch paths must not substitute for closing missing acceptance.
