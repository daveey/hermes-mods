# Panel latency, producer contention and staleness diagnosis

## Diagnose a stale panel (board and panel disagree)

1. Read feed timing on the host (no Desktop token needed): `~/.hermes/session-panel/timing-feed-<role>-<profile>.json`, rewritten after every pass: `tick_started_at`, `tick_duration_s`, `producer_s`, `producer_chats`, and `recent` (last 32 pushes: `rev`, `at`, `sessions`, `pass_started_at`). Freshness of one write is the `recent` entry naming its chat minus the write's commit time; `/status` and `/changes` return 401 from a hub shell.
2. Read the last published models from `feed-<role>-<profile>.json` in the same dir. It is two JSON lines (header, then body): `json.loads(text.splitlines()[1])`, not `json.load` (fails with "Extra data"). The chat's model is `bundles[<session>].bundle.model` (`sections`, `header`), with `bundle.computed_at` and `bundle.tasks`/`cards`.
3. "Panel says nothing running / no dependency shown" or a card listed Waiting as `status unknown (no run identity | source expired) · last known: <state>` while the board says otherwise: compare the card's claim/link/park/archive event times (`task_events.created_at`) with the chat's bundle `computed_at` and with its `board_recent` entries in the timing file (`admitted_at`, `pass_started_at`, `latency_s` per session). Whole-feed passes can take minutes, so a correct reducer paints a snapshot read seconds before the transition; the header can still be right because it comes from the fresher canonical status. Confirm by computing the current snapshot yourself (below); if it is right, the fault is producer freshness, not classification: comment the timeline on the open feed-freshness card rather than filing a new one.
   Check bundle age before diagnosing run-less evidence on parked-state cards (scheduled/triage/blocked/review/ready/todo). Parked hub cards can legitimately carry a run-less `kanban.card` observation. The reducer preserves historical board detail beyond 60 seconds only for producer-gap evidence, with explicit as-of/panel-data age. A CI/deploy/clock wait painted in the fallback colour (amber/grey instead of light blue) next to "(panel data Nm old)" means that aged branch dropped `wait_kind`. Keep the cutoff for delivery colour above the quiet re-read cadence (`QUIET_FULL_EVERY_S` in `dashboard/feed.py`). A quiet chat's bundle is legitimately minutes old, so a 60 s cutoff strips the colour from every quiet chat. Test ages on both sides of the cutoff, and drop agent-owned waits at 60 s as before. Stale running cards, contradictions, unavailable board status and future clocks remain unknown. On older deployments, an aged parked row can instead fall through to the misleading `status unknown (no run identity)` label; compare deployed reducer bytes and bundle age before attributing that label to an executor defect.

   Fresh compute with the deployed code, read-only, from the core venv (put it in a scratch script and run it with `cd ~/.hermes/hermes-agent && hermes --run-module cProfile -o /dev/null <abs>/probe.py <session>`; about 12 s on a busy hub):
   ```python
   D='~/code/hermes-mods/plugins/session-panel/dashboard'  # expanded path
   sys.path.insert(0, D)
   spec = importlib.util.spec_from_file_location('pa', D + '/plugin_api.py')
   pa = importlib.util.module_from_spec(spec); sys.modules['pa'] = pa  # register before exec
   spec.loader.exec_module(pa)
   b = pa._load_feed().Feed(pa.CoreReaders(), emit=lambda p: None).compute(SESSION)
   b['model']['header'], b['model']['sections']
   ```
   `pa.CoreReaders().linked(lineage)` / `.done(lineage)` give the raw task inputs when you only need the source side.
4. A remote parent (a card on a worker board) is absent from local `tasks`; `hermes kanban show <id>` says "no such task". Its status lives in hub `kanban_sync_remote_parents` (and `kanban_move_parent_results`, `task_chat_links`): query those directly instead of scanning every board DB (that scan timed out). To read the card itself, run `~/.hermes/bin/hub-worker-exec <worker> -- bash -lc 'hermes kanban show <id> --json'`; the `--` is required. If a parked card (scheduled/todo/blocked) shows as `waiting for status from <worker>` because it lives only in a worker's DB, treat that as a placement defect, not a label defect. Parked cards belong on the shared queue, where any worker can pick them up, and a card left on one worker is stranded if that worker goes away. File the fix at the point where the card was created, and check open placement cards first. A label-only fix hides the problem.
5. Sidebar row with a violet "Done, not yet seen" square but nothing new: the square is `kanban_unseen`, the count of the chat's `tui` subscriptions in `kanban_notify_subs` whose card has a result event (`completed`/`blocked`/`gave_up`/…) with `id > last_event_id`. The grey dot is the settled outcome; a parked card shows grey. On the backend's kanban.db, compare each subscription's `last_event_id` with that card's newest result event. If all are caught up, the Mac's row is stale. Count `conn=<gateway> ... Timed out connecting` lines per 10 minutes in the Mac's `~/.hermes/logs/desktop.log` through `tailnet_exec`: refreshes that never land keep the old row. When the hub side is caught up, the fix is the Mac-to-hub transport, not the square renderer.
6. Grey/"waiting" row dot while the panel lists a remote (worker-homed) card as running: the dot comes from the stored canonical outcome, and for remote cards it is re-derived only by `notice_fanout.card_change_pass` from the unloaded sweeper loop (`kanban_unloaded.INTERVAL_S`, 60 s), plus replica push lag. Compare `hermes sessions outcome <sid> --json` (`outcome.at`, `kind`, `reason_codes`) with the card's `claimed`/`spawned`/`worker_result`/`scheduled` event times in `kanban/sync-shadow/<board>.db`. Worker cards run in short bursts between CI/review parks, and the panel's elapsed time counts from the card's first start, not the current run. If the outcome predates the claim by under ~2 min, it is that lag, not a `_verdict` regression. Confirm by checking that `_read_card_items([sid])` now yields the card as `running`.

7. "Session status is taking longer than usual · Retry" (`PendingModel`, not loading): the focused chat has no cached model after `feedFocus`'s three quick attempts. First split compute from delivery: if `feed-<role>-<profile>.json` already holds `bundles[<session>]`, the hub computed it and Desktop failed to read it. Then read the timing file's `board_recent` latency and serve CPU, and count `Timed out connecting` lines in the Mac's `desktop.log` (user-steps/kanban GETs are a proxy for transport starvation). Panel-side peek failures go to the renderer console via `log()`, not `desktop.log`, so do not grep it for them. Desktop now treats a peek timeout like a missing feed (full catch-up) and keeps retrying with backoff while focused; Retry stays visible but is not required. Pushes still fire only on model changes. A stuck Retry after those client retries is serve/delivery load: route it to the open serve-CPU owner, not another client auto-retry card.

## Producer design rules

- Preserve runtime-source absence during decision-only commit-time carriage: copy `processes` only if the held bundle actually contains that key. Inserting `[]` turns an absent producer into a known-empty observation and defeats canonical no-op comparisons, causing unnecessary reduction/publication. Test absent and explicitly empty inventory through both interactive and background refresh, retaining unchanged revision/push counts; run these controls with and without core, since core-backed adapters may populate the field and hide the regression.

- Settle runtime admission stamps and probe times only after the captured process inventory wins publication. A newer decision-only read can supersede its canonical sequence while carrying an empty pre-birth list; consuming the checkpoint stamp then permanently loses the birth because live-only timers never arm. Retain a bounded immediate retry for superseded captures even with empty published inventory; decision-only reads must carry processes at commit rather than claim authority over their read-start copy. Test birth and exit interleavings through real Feed publication, stable-stamp recovery, and forgotten/lineage-retired captures that must not arm ghost retries.

- Re-probe real process evidence on admitted birth/exit changes as well as before a live observation's TTL. An immediate birth after an empty sidebar probe can land inside the process adapter's short cache; a periodic schedule keyed only to returned process rows then never arms. Exercise empty cached inventory → actual terminal(background=true) birth without advancing the cache clock, plus a hold beyond the observation TTL and intentional stop. Distinguish backend/reducer lifecycle proof from mounted/native sidebar proof; preserve failed setup output and clean the disposable session even when an assertion or process-stop call fails.

- Fail closed in the mounted Panel before the first heartbeat: older cached models can lack source freshness metadata, so an unspecified voucher keeps a legacy running header indefinitely. Test actual Panel with legacy cache and no heartbeat, not only renderModel with an explicit false voucher. Keep restored/expired/excluded and fresh controls; transport heartbeats never renew bundle computed_at.

- Treat ceiling chat count as a work bound, not a latency bound. Preserve a real-loop slow-producer regression plus an event-blocked producer while an unrelated write publishes; fast fakes alone hide head-of-line blocking. When isolating canonical ceiling work, test same-owner/ancestor claims, hot handover, forgotten completions, finite asynchronous retries and wake clear/drain races. Retain other-chat producer obligations when an in-flight stamp read consumes a concurrent outcome write; do not blindly re-admit the producer's own completed writes.

- Test sync-bookkeeping invalidation with real replica SQL and canonical projection adapters. A `pulled_at`-only commit must carry `synced_at` without renewing `computed_at`/execution evidence or hydrating every chat. Admit board-shadow writes even without a hub/ledger write. Canonical hub rows may lack `source='replica'`, and selection may add `source='origin-obligation'`: match observation producer plus owner/profile/board/card/session, not a raw source label or bare card ID. Keep true stale/status/receipt changes semantic, allow legitimate clock regression on source reset, and exercise a real concurrent producer publishing an older capture after a newer observation.
- When moving reconciliation out of presentation, admit producer work independently of outcome/request invalidation: session membership can change without either changing. Exclude the producer's own action-store writes, capture source stamps before writes, and propagate canonical deferred/partial results rather than treating a normal return as success. Keep failure retries bounded and preserve the event cursor. A globally source-gated producer is only an intermediate seam, not per-session batching acceptance.
- When widening per-lineage readers to a whole-feed union, bind owner scopes as one JSON parameter with `json_each`, not two SQL variables per owner. Prove the union at SQLite's 999-variable limit, preserve per-lineage order/profile fences and missing-own-session errors, and deep-copy shared parent presentation. A closed ActionStore snapshot alone does not prove core-board batching or selective source reconciliation.
- Prefer one short-lived read-only connection per source DB per producer pass, with set-based reads for all relevant sessions/cards; fetch results and close before Python processing. Do not introduce persistent reader connections as a latency optimization. Cache board projections until their source changes and make producer wakeups change-driven.
- Keep the scoped source producer no weaker than "any source write admits every chat": the source stamp is captured before the board/external reads, so admit chats those reads marked dirty even when the stamp had not moved, re-admit `_reconcile_deferred` on any moved stamp, and compare lineage with the one last reconciled under (the held bundle may already have adopted the new one).
- Preserve canonical time/courier liveness when admitting source reconciliation per chat: track each chat's last actual producer call, not its last unaffected-stamp settlement. On a real source write, re-admit chats past the canonical mirror's 60 s safety ceiling; this is not an idle polling timer. Exercise a remote answer left `remote-retiring`, let stable-refusal time elapse without moving request stamps, then deliver unrelated writes and assert final retirement plus a replacement ask. Input keys alone cannot represent courier receipts or unkeyed mirror fallbacks.
- Do not use sparse disk bundle persistence as the timestamp of an in-memory model publication. Retain raw source-event creation, locally observed receipt, admission, publish/emit revision and exact owner/session together; disk observer matches are upper-bound controls only and may reflect delayed persistence. An unchanged restored bundle observed after a write does not establish current publication, and expected raw task status does not prove the corresponding model row's classification. Count unmatched and superseded events explicitly.
- Treat `session_panel.compute.*` loop counters as global across normal feed, board-lane and request callers, not exclusive feed-thread costs. Compare them with per-family CPU before assigning a hot path; sibling stages can exceed the feed family's total without accounting duplication. Use caller-thread `time.thread_time()` around real reader calls in a bounded replay for localization, retain production/replay distinctions, and never sum a reader with its nested core spans. A cProfile cumulative ranking alone does not establish caller-exclusive CPU or justify a cache. Run diagnostic replays after, not during, the acceptance census to avoid changing its contention.
- Sum CPU across every process birth and thread birth/generation, including transient workers that exit before the last sample. Compare whole-process counters with per-family lower bounds; a short-lived thread's own observed CPU percentage is not its whole-window duty. Retain sampling races and gaps, and never select only the newest or least-busy serving process.
- Measure the authenticated Desktop listener separately from the always-on proxy. Retain process birth identity, summed per-thread context-switch deltas and process CPU alongside route latency. A warm hub-local `/changes` response below 500 ms does not prove installed Desktop click-to-render, cold hydration or restart recovery. Preserve raw samples and label those acceptance gaps explicitly.
