# Board-custody diagnosis

1. Read the target and nominated repair producer. An archived producer cannot deliver a repair; posting evidence there does not create an active handoff. For cross-gateway owner discovery, capture `hermes-hub tasks --json` with `subprocess.run(..., capture_output=True, text=True)`, parse stdout as JSON, then print only matching open cards' IDs, gateways, statuses and latest comments. Add `--all` only when historical records are needed. Filter before terminal capture: an unfiltered fleet dump can exceed the saved-output limit and leave truncated, unparsable JSON; the filtered live inventory can also reveal an existing repair filed during your investigation.
2. Before delegating custody diagnosis, have the authorized owning context run `hermes kanban --board <board> sync status`. Supply sanitized mode, board identity, gateway and the exact lifecycle refusal to the repair card. Do not equate a private board with an unsynced board: shadow mode can explain a primary/local-only refusal without proving the guard is defective.
3. If a board-pinned worker lacks evidence, collect one consolidated export in the authorized owning context: board mode, target status/current run, latest run outcome and end time, admission/claim correspondence, exact transition results, both dependency directions and unmet acceptance. For a causal audit, include relevant origin message/tool rows with stored IDs/timestamps and installed revisions; distinguish stored timestamps from delivery proof and label unavailable fields. Exclude unrelated content and secrets. Attach with `hermes kanban --board <repair-board> attach <repair-card> <export-path>`, then verify with `attachments <repair-card>`. This lets the worker consume authorized evidence without bypassing isolation or repeatedly returning for one missing field. Re-read after the handoff before unblocking: the reply may already have resumed its worker.
4. Use the evidence to narrow the investigation before resuming it. Do not change sync enrollment or relax custody checks merely to make the operation pass.
5. Distinguish timestamp expiry from canonical lease release. The Board deliberately keeps a dark/offline holder's lapsed lease for up to `DARK_HOLD_MAX_MS` (currently 12h), with a reassert grace on return. Read the authenticated canonical task and leases row before diagnosing a reaper gap: a retained row still fences foreign lifecycle writes. Do not remove that fence to recover a sleeping worker. An explicitly authorized early recovery uses the existing operator lease-reset route, which requires operator Access authority; a settings-bound service token or ordinary gateway key does not grant reset access. A local CLI success is not recovery proof: read back canonical status/run/lease after sync.

This procedure establishes diagnostic evidence, not a working retention operation. Claim a durable hold only after its supported operation returns a receipt and exact-target readback confirms it; a running repair or accepted comment is not that proof.
