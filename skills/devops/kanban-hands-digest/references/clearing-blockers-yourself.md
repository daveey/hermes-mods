# Clearing blocked cards yourself

Classify each blocked card by the event that stopped it (`select kind,payload from task_events where task_id=? and kind in ('blocked','gave_up','crashed') order by id desc limit 1`), not by its body.

| Stop cause | Action |
|---|---|
| `gave_up` with a provider 429 / "usage limit resets in ~Nh" tail | Read the admitting worker's eligible, funded class routes and quota/pacing holds. Remove legacy exact-model/provider overrides and mandatory requirements with `hermes kanban set-model <id> none`, or `hermes kanban set-model <id> class:<level> --no-mandatory`; use no selector or an optional `class:deep`, `class:standard` or `class:fast` preference, with provider omitted and never mandatory. Check queued `todo`/`scheduled` siblings for the same legacy restrictions. Preserve real quota/billing holds; do not change interactive chat model guidance or add concrete fallback routes to force a Kanban start. Verify the saved routing policy, actual claim and resolved run route, not just a scratch completion. |
| `ready`/`running` card that never progresses, with a run every ~1 min ending `outcome='rate_limited'` (`select outcome,count(*) from task_runs where task_id=? and started_at>strftime('%s','now')-3600 group by 1`) | A quota-wall spawn loop: the dispatcher requeues neutrally, so it never gives up and the card looks ready or waiting. Read the retry-after in `~/.hermes/kanban/logs/<id>.log`. Audit affected cards in every status, including `review`, for legacy exact-model/provider and mandatory restrictions; restore capability-only routing as above. Inspect the effective `model_tier` and resolved route rather than assuming the default applies to every tier. For reviewers, retain genuine independent run/session custody and the supported review handoff; a different model is not independence. If every eligible class route is held, wait through supported deferral instead of bypassing quota. |
| `needs_input` saying "continuation limit reached" | This is an agent issue, not a user ask. A plain `hermes kanban unblock` is enough for a first exhaustion, because the blocked run breaks the consecutive-continuation streak. If the card has exhausted before, or its checkpoint's NEXT list is still large, split the remaining items into bounded slice cards instead. Give each slice one existing worktree (no two slices editing the same tree), a body that says read the checkpoint and do not redo finished phases, and an exhaustion instruction the card can actually follow. A goal_mode card's worker can't block kind=transient: the kernel rejects it, and the worker falls back to needs_input, which paints the session red again. So either create slices without `--goal`, or tell goal slices "if continuation runs out, block kind=time with the checkpoint". Then `hermes kanban link <slice> <root>` for each, comment on the root that it now owns only integration, review, ship and live acceptance, and unblock it. The root goes `todo`, which counts as active and not human-blocked, so the session stops showing red. |
| `gave_up` "exited cleanly without kanban_complete" (protocol violation) | Read the tail of `~/.hermes/kanban/logs/<id>.log`. If runs die at ~60 s on a heavy test command (`[exit -15]`), comment: run heavy tests backgrounded or memory-capped, single fork, never broad `pkill`/`kill 0`, checkpoint by comment after heavy steps, and always end with a terminal kanban call. Then unblock; the worker re-verifies its prior work. |
| Any blocked card (often kind `needs_input`, so it looks like David's ask and paints red) whose reason starts "Held in ready by the respawn guard" (`active_pr`, `blocker_auth`) | Not a person: the guard's hold cap auto-blocked it. For `active_pr` on a card with zero `task_runs` (a review card whose handoff names the PR), unblock or re-`assign` it (a handoff event lifts the hold). For `blocker_auth` with a quota / rate-limit error while other cards complete: if the live checkout contains the quota-guard fix, the dispatcher releases these itself; otherwise null `last_failure_error` and `consecutive_failures`, comment, and unblock (the guard re-matches the quota text when `merge-base --is-ancestor` says the checkout is behind). Real auth (401, invalid key) stays blocked. Split: kanban-orchestrator's `idle-cards-triage` reference §2. |
| `capability`: the profile can't write that code | `hermes kanban reassign <id> default --reason …`, then unblock. If a worker created the card (`creator_task_id` in its `created` event), comment on that creator card to assign any further code, mirror or CI cards to default, or it keeps creating misrouted cards. |
| `needs_input` asking David to merge a PR or push main "because this profile may not" | That restriction belongs to the profile, not to the user. Reassign to a profile with merge authority under the normal PR/CI workflow, and comment "merge once required checks pass, then verify main CI". |
| Needs a host the gateway can't SSH to, or "reconnect Desktop so session X can receive" | `cross_session read` the target session first; if it answers, the relay works. Comment the route (cross_session to a session on that host's gateway, e.g. the one already running `bb land` merges), then unblock. |
| Only part of a card needs human input or privileged diagnostics | Keep that exact gate on its existing human-action card. Amend the implementation owner's BODY with a concrete independent code/test slice, exclusions and unchanged final acceptance; then unblock that same owner and verify a new claim. A generic "finish everything else" comment leaves the next worker following the old blocked contract. Do not treat independent progress as host recovery or final completion. |
| `scheduled` card whose wake probe always exits 1 but `task_wake_checks.last_out` shows a traceback, `syntax error` or `incomplete input` | The probe is broken, not "not yet". The usual cause is SQL or quoted args passed through `ssh host '...'`: ssh joins argv and the remote shell re-splits the quotes. Replace it with an argv-only probe (`ssh hub python3 .hermes/scripts/kanban_wait.py task <id>`, or `board-empty <board>`; exit 0 met / 1 not yet / 2 unknown). Run the new probe once by hand before re-parking. A scheduled card can't be re-scheduled directly: `unblock` first, then `schedule --wake-check`. When a PR is replaced, inspect the stored `wake_check`, not just the workspace waiter script: the dispatcher may execute an embedded old PR URL. Replace that stored target and read back the scheduled event's command and deadline; closure of the superseded PR is not delivery of its replacement. |
| `blocked`/`continuation_exhausted` whose reason only says "Waiting on t_x" | A wait, not a block. Re-park it on a probe of t_x (row above) so it wakes on its own. |
| `ready` cards stay unclaimed while workers sit below the concurrency cap (MacBook or hub) | Check for the core-update drain hold: `~/.hermes/core-update/drain-hold` (a JSON file directly in that dir, not under `holds/`). While it exists the dispatcher claims nothing new. A live Desktop chat or one long worker keeps the drain from ever finishing, so the whole pool starves. Release it with `mv` into `~/.hermes/cache/` (the update just retries later), wait about 2 min, then read back the claims and the worker count. |
| A remote-gateway session needs a sudo prompt or a hardline-blocked command (`mkfs`) | That session can't open `run_in_user_terminal`; only the owner's chat can. From the owner chat, `cat` + `sha256sum` the remote guard script and match it against the hash the session sent, then run `ssh -t <host> 'sudo <script>'` via `run_in_user_terminal`. Read back the result yourself (`blkid`, `findmnt`) before messaging the session. Approval of the resource (e.g. a new volume) covers formatting it; a destructive rotate or reset needs its own explicit go. |
| Spend-hold/triage card whose decision is already recorded (renewed scope + spend producer's run window in comments), but the card lives on another gateway (only in `sync-shadow`) | Hub `hermes kanban promote` answers "task not found" and `kanban_supervisor_request` refuses `not_foreign`: apply it on the card's home gateway. `tailnet_exec host=<home>` with `export PATH=$HOME/.local/bin:$PATH` first (the non-login shell lacks `hermes`): `promote --dry-run --seen <newest comment id>`, then `spend-budget <id> --runs <prior runs + window> --seen <id> --reason ...`, then `promote --seen <id> "<decision comment refs>"`. Read status back on that gateway; sync-shadow lags. Then comment + archive its spend-decision card. `hermes kanban renew-scope` can refuse `not_scope_authority` even from the owning chat (`origin-adopt` grants no scope authority; mandate comment ids differ per replica): don't retry it, file a follow-up card parented on the Hermes fix card instead. |
| Comment/archive refused because the card "lives" on another gateway | Run the CLI on its home: hub = local `hermes kanban`; a Mac = `tailnet_exec` with the PATH export above; a pool worker = `~/.hermes/bin/hub-worker-exec <worker> --timeout N -- <script-file>` (an inline command without `--` is refused; a script file avoids nested quoting); on a Mac `zsh -lc 'hermes kanban …'` also gets PATH. The hub CLI `hermes kanban comment` on a foreign card does work, because it syncs a canonical comment to the home, so you can leave the trail comment there; archive still has to run on the home. A stale `triage` card can't be completed (`complete` answers "unknown id or terminal state"): comment the evidence, then `archive` it. Several cards may have different homes: read each status back on its home. |
| Owner decision / scope choice | Ask inline with `clarify` (see SKILL.md), then record and complete. |

After fixing one misrouted card, sweep for its siblings before they block: `select id,status,title from tasks where assignee in (<narrow/sandboxed profiles>) and status not in ('done','archived')`. Worker-created follow-ups inherit the same wrong assignee, and each one that blocks turns the session red again.

Unblock in one call (`hermes kanban unblock <ids…> --reason …`). Read back status, `consecutive_failures`, model override and actual claim. When a card this chat depends on stays ready behind a full pool, inspect its current priority before raising it; a fixed numeric priority can accidentally lower it. If the queue still prevents progress, execute a bounded slice in this chat or a direct subagent. Re-read ownership before edits: if the dispatcher starts the original worker, hand it the branch, tests and review artifacts rather than race publication. A queued card is not an executing fix.

## Reconciling a delivered Board-owned landing tracker

Use this only when delivery is already verified and the local mutation tool reports a foreign replica. A replica is evidence, not the writable owner. Delegated children must return the receipt to the parent operator, not bypass their mutation fence.

1. Read the authoritative row with the installed Board client: `from hermes_cli.kanban_sync_client import Hub, load_identity`; `hub = Hub(load_identity())`; `hub.row_evidence(board, 'tasks', task_id)`. Confirm the parent is done and the tracker has no live lease/run. Scan reverse dependency edges and cross-gateway references before closure.
2. Verify actual landed revisions and installed bytes. If an inaccessible handoff patch was rebuilt and independently reviewed, record the replacement commit explicitly rather than claiming the original SHA landed.
3. For an authorized parent operator, inspect the current semantic API before using `hub.ops(board, [op])`. The verified completion shape is `{'client_op_id': stable_id, 'op': 'complete', 'task': task_id, 'result': evidence_summary, 'summary': short_summary, 'metadata': evidence_metadata}`. Use it only for fulfilled acceptance; do not use it to evade a completion refusal or mark missing proof successful. Keep server parent/lease checks intact.
4. Require an `applied` receipt, then independently call `row_evidence` again and verify `status='done'` plus the exact result. Do not repeat publication or deployment merely to clear bookkeeping.

## Fleet inventory and session mapping

1. Discover connected gateways with `cross_session(action="list")`, then inventory each gateway's board stores read-only. Do not use a recent-session list as the audit population: high-volume worker/API sessions can crowd out older Desktop chats.
2. Save per-gateway JSON containing every unfinished task (`status NOT IN ('done','archived')`), dependency links, recent events/comments/runs, wake checks and `kanban_notify_subs`. Deduplicate database paths by resolved path; retain read errors as coverage gaps.
3. Read session metadata from each gateway/profile's `state.db`. Join notification subscriptions to sessions by **gateway + profile + session ID**: a bare `chat_id` is local to its notification route; a qualified one supplies the remote route. Verify gateway aliases against discovery. Count unique chats separately from cards and subscriptions; filter `source='desktop'` and unarchived state when reporting affected visible chats.
4. Filter and project records before printing, not after transport. For owner discovery, filter unfinished status and title first, then emit only `id`, `title`, `status`; matching `str(row)` also searches long bodies and can return megabytes of unrelated history. For example:
   ```bash
   hermes kanban list --json | python3 -c 'import json,sys; d=json.load(sys.stdin); rows=d if isinstance(d,list) else d.get("tasks",[]); print(json.dumps([{k:r.get(k) for k in ("id","title","status")} for r in rows if r.get("status") not in ("done","archived") and "accounting" in r.get("title", "").lower()]))'
   ```
   Keep full histories and subscription arrays in an artifact; print counts and compact classifications, then expand selected records. Apply the projection on the worker before SSM transport too: full `kanban show` histories can exhaust its output cap before recent evidence arrives.
4a. "Which red cards aren't linked to a session?": per board, take red cards (`blocked`, `gave_up`, `triage` with human `block_kind`) and their `task_chat_links` rows; a card is ownerless when it has no row with `released=0`. A live-looking link can still be dead: look up each linked `chat_session` in `state.db` `sessions` and treat `end_reason='startup_orphan_reap'` (or `archived=1`) as no owner. Inspect columns with `pragma table_info(<table>)`, never `.schema`: the kanban tables carry sync triggers that dump tens of KB per board.
4b. Distinguish a real project chat from a synthetic fallback owner. A `kanban_owner_*` session titled `Kanban owner: <producer>` is a durable owner, not an ownerless card, but may explain why product work appears under a generic terminal/producer heading. Check both `tasks.session_id` and unreleased `task_chat_links`; either alone can omit the effective association. If the existing product chat's mandate covers the card, attach it with `hermes-hub adopt-task <owner-gateway> <owner-profile>/<board>/<task> --origin-session <existing-chat-id> --origin-profile <chat-profile> --id <stable-request-id>`. Preserve blocked status and acceptance. A queued adoption or `origin_bind_pending` is not completion: run the normal `hermes-hub sync` cycle and inspect `hermes-hub outcomes --id <same-request-id>` until the exact origin receipt is accepted with `handoff_complete=true`; retain the same identity across retries. Then verify membership with `hermes kanban chat-tasks <existing-chat-id> --expect <task-id> --json`, projecting the returned array to those exact IDs before printing. A successful projection proves backend chat membership, not a Mac sidebar repaint. Do not rewrite `session_id` merely because it still contains a fallback value after the qualified link succeeds.
5. Re-read exact targets before transitions. Read back new runs after recovery; snapshot inventory and queued recovery are not proof that all sessions are fixed.
6. For "why are sessions neither blocked nor done", run `~/.hermes/bin/session-idle-check` (private repo; `--json` for the full report). It recomputes the sidebar's own annotations on every gateway in `connections.json` and resolves each card a session waits on, recursively across gateways and through wake-probe references, to RUNNING (live worker pid + fresh heartbeat), BLOCKED (a concrete human ask), WAITING (a probe that ran recently, a future wake, or a validly waiting parent) or VIOLATION. Fix each violation, then re-run until it exits 0. Known causes with an open fix card are listed in `~/.hermes/state/session-idle-check/tracking.json`; remove an entry once its fix is live.
7. A fix that a card reports as shipped is not containment until each host reads it back with `git -C ~/.hermes/hermes-agent merge-base --is-ancestor <sha> HEAD`. The macOS updater defers while workers or Desktop turns are busy, so a saturated host can stay behind for hours. Keep supported containment (capability-only routing, re-assigns) in place until the readback passes, without bypassing quota or review custody.

## Sign-in blockers (hub-session-sync sites)

1. Check: `/usr/bin/python3 ~/.hermes/hub-session-sync/hub_session_sync.py check <site>` (use the interpreter that has PyYAML; exit 0 = signed in).
2. The hub agent browser (`browser_exec`) already holds his Google sessions. Open the site's login page and choose "Sign in with Google". In the account chooser, click the row with JS: `document.querySelector('[data-identifier="<email>"]').click()`, or walk text nodes to that row's `role=link` ancestor. Coordinate clicks often miss there. The browser is shared with other sessions, so open your own tab with `new_tab` and re-read `location.href` before each step.
3. Verify it is HIS existing account (an existing plan, usage or billing history), not a freshly created one. If it is new, sign out and try the other address.
4. Re-run `check`, then `hub_session_sync.py resolve <site>`; the blocked card completes itself. Read its status back.
5. GitHub's OAuth "Authorize" button stays disabled for automated input. That is an anti-clickjacking guard, so never remove the `disabled` attribute; use a different SSO provider instead.
6. `run_in_user_terminal` only runs from the owner's own chat. From a dispatch session, do the hub-side route above rather than handing him a command to paste.
