# Clearing blocked cards yourself

Classify each blocked card by the event that stopped it (`select kind,payload from task_events where task_id=? and kind in ('blocked','gave_up','crashed') order by id desc limit 1`), not by its body.

| Stop cause | Action |
|---|---|
| `gave_up` with a provider 429 / "usage limit resets in ~Nh" tail | Repin to a working subscription model (`hermes kanban set-model <id> <model> --provider <p>`), after a one-line live check of that model (`hermes chat -q "Reply with exactly: OK" -m <model> --provider <p> --quiet`). Also repin queued `todo`/`scheduled` cards pinned to the walled provider, or they fail on dispatch. If the gateway's root model has an empty fallback chain, add one: `hermes config set fallback_providers '[{"provider":"openai-codex","model":"gpt-6-astra"}]'`, then `hermes fallback list`. |
| `ready`/`running` card that never progresses, with a run every ~1 min ending `outcome='rate_limited'` (`select outcome,count(*) from task_runs where task_id=? and started_at>strftime('%s','now')-3600 group by 1`) | A quota-wall spawn loop: the dispatcher requeues neutrally, so it never gives up and the card looks ready or waiting. Read the retry-after in `~/.hermes/kanban/logs/<id>.log`. Repin every card whose latest run is `rate_limited` (all statuses, including `review`) to a live provider. Setting `kanban.default_model` is not enough: review, keep-pattern and retry tiers resolve to `model: null` (the profile's chat model) in the `model_tier` event. |
| `needs_input` saying "continuation limit reached" | This is an agent issue, not a user ask. A plain `hermes kanban unblock` is enough for a first exhaustion, because the blocked run breaks the consecutive-continuation streak. If the card has exhausted before, or its checkpoint's NEXT list is still large, split the remaining items into bounded slice cards instead. Give each slice one existing worktree (no two slices editing the same tree), a body that says read the checkpoint and do not redo finished phases, and an exhaustion instruction the card can actually follow. A goal_mode card's worker can't block kind=transient: the kernel rejects it, and the worker falls back to needs_input, which paints the session red again. So either create slices without `--goal`, or tell goal slices "if continuation runs out, block kind=time with the checkpoint". Then `hermes kanban link <slice> <root>` for each, comment on the root that it now owns only integration, review, ship and live acceptance, and unblock it. The root goes `todo`, which counts as active and not human-blocked, so the session stops showing red. |
| `gave_up` "exited cleanly without kanban_complete" (protocol violation) | Read the tail of `~/.hermes/kanban/logs/<id>.log`. If runs die at ~60 s on a heavy test command (`[exit -15]`), comment: run heavy tests backgrounded or memory-capped, single fork, never broad `pkill`/`kill 0`, checkpoint by comment after heavy steps, and always end with a terminal kanban call. Then unblock; the worker re-verifies its prior work. |
| Any blocked card (often kind `needs_input`, so it looks like David's ask and paints red) whose reason starts "Held in ready by the respawn guard" (`active_pr`, `blocker_auth`) | Not a person: the guard's hold cap auto-blocked it. For `active_pr` on a card with zero `task_runs` (a review card whose handoff names the PR), unblock or re-`assign` it (a handoff event lifts the hold). For `blocker_auth` with a quota / rate-limit error while other cards complete: if the live checkout contains the quota-guard fix, the dispatcher releases these itself; otherwise null `last_failure_error` and `consecutive_failures`, comment, and unblock (the guard re-matches the quota text when `merge-base --is-ancestor` says the checkout is behind). Real auth (401, invalid key) stays blocked. Split: kanban-orchestrator `references/idle-cards-triage.md` §2. |
| `capability`: the profile can't write that code | `hermes kanban reassign <id> default --reason …`, then unblock. If a worker created the card (`creator_task_id` in its `created` event), comment on that creator card to assign any further code, mirror or CI cards to default, or it keeps creating misrouted cards. |
| `needs_input` asking David to merge a PR or push main "because this profile may not" | That restriction belongs to the profile, not to the user. Reassign to a profile with merge authority under the normal PR/CI workflow, and comment "merge once required checks pass, then verify main CI". |
| Needs a host the gateway can't SSH to, or "reconnect Desktop so session X can receive" | `cross_session read` the target session first; if it answers, the relay works. Comment the route (cross_session to a session on that host's gateway, e.g. the one already running `bb land` merges), then unblock. |
| Only part of a card needs human input or privileged diagnostics | Keep that exact gate on its existing human-action card. Amend the implementation owner's BODY with a concrete independent code/test slice, exclusions and unchanged final acceptance; then unblock that same owner and verify a new claim. A generic "finish everything else" comment leaves the next worker following the old blocked contract. Do not treat independent progress as host recovery or final completion. |
| `scheduled` card whose wake probe always exits 1 but `task_wake_checks.last_out` shows a traceback, `syntax error` or `incomplete input` | The probe is broken, not "not yet". The usual cause is SQL or quoted args passed through `ssh host '...'`: ssh joins argv and the remote shell re-splits the quotes. Replace it with an argv-only probe (`ssh hub python3 .hermes/scripts/kanban_wait.py task <id>`, or `board-empty <board>`; exit 0 met / 1 not yet / 2 unknown). Run the new probe once by hand before re-parking. A scheduled card can't be re-scheduled directly: `unblock` first, then `schedule --wake-check`. |
| `blocked`/`continuation_exhausted` whose reason only says "Waiting on t_x" | A wait, not a block. Re-park it on a probe of t_x (row above) so it wakes on its own. |
| `ready` cards stay unclaimed while workers sit below the concurrency cap (MacBook or hub) | Check for the core-update drain hold: `~/.hermes/core-update/drain-hold` (a JSON file directly in that dir, not under `holds/`). While it exists the dispatcher claims nothing new. A live Desktop chat or one long worker keeps the drain from ever finishing, so the whole pool starves. Release it with `mv` into `~/.hermes/cache/` (the update just retries later), wait about 2 min, then read back the claims and the worker count. |
| A remote-gateway session needs a sudo prompt or a hardline-blocked command (`mkfs`) | That session can't open `run_in_user_terminal`; only the owner's chat can. From the owner chat, `cat` + `sha256sum` the remote guard script and match it against the hash the session sent, then run `ssh -t <host> 'sudo <script>'` via `run_in_user_terminal`. Read back the result yourself (`blkid`, `findmnt`) before messaging the session. Approval of the resource (e.g. a new volume) covers formatting it; a destructive rotate or reset needs its own explicit go. |
| Owner decision / scope choice | Ask inline with `clarify` (see SKILL.md), then record and complete. |

After fixing one misrouted card, sweep for its siblings before they block: `select id,status,title from tasks where assignee in (<narrow/sandboxed profiles>) and status not in ('done','archived')`. Worker-created follow-ups inherit the same wrong assignee, and each one that blocks turns the session red again.

Unblock in one call (`hermes kanban unblock <ids…> --reason …`). After about 3 minutes, read back status, `consecutive_failures` and the model override. Queued `ready` cards behind the concurrency limit are fine.

## Fleet inventory and session mapping

1. Discover connected gateways with `cross_session(action="list")`, then inventory each gateway's board stores read-only. Do not use a recent-session list as the audit population: high-volume worker/API sessions can crowd out older Desktop chats.
2. Save per-gateway JSON containing every unfinished task (`status NOT IN ('done','archived')`), dependency links, recent events/comments/runs, wake checks and `kanban_notify_subs`. Deduplicate database paths by resolved path; retain read errors as coverage gaps.
3. Read session metadata from each gateway/profile's `state.db`. Join notification subscriptions to sessions by **gateway + profile + session ID**: a bare `chat_id` is local to its notification route; a qualified one supplies the remote route. Verify gateway aliases against discovery. Count unique chats separately from cards and subscriptions; filter `source='desktop'` and unarchived state when reporting affected visible chats.
4. Keep the full subscription arrays and histories in the artifact, not tool stdout. Print board/status counts and compact per-card classifications, then expand only the records needed for a decision. Full per-card subscription dumps repeatedly exceed capture limits and bury the blockers; an aggregate computed from the saved JSON preserves coverage without that cost.
5. Re-read exact targets before transitions. Read back new runs after recovery; snapshot inventory and queued recovery are not proof that all sessions are fixed.
6. For "why are sessions neither blocked nor done", run `~/.hermes/bin/session-idle-check` (private repo; `--json` for the full report). It recomputes the sidebar's own annotations on every gateway in `connections.json` and resolves each card a session waits on, recursively across gateways and through wake-probe references, to RUNNING (live worker pid + fresh heartbeat), BLOCKED (a concrete human ask), WAITING (a probe that ran recently, a future wake, or a validly waiting parent) or VIOLATION. Fix each violation, then re-run until it exits 0. Known causes with an open fix card are listed in `~/.hermes/state/session-idle-check/tracking.json`; remove an entry once its fix is live.
7. A fix that a card reports as shipped is not containment until each host reads it back with `git -C ~/.hermes/hermes-agent merge-base --is-ancestor <sha> HEAD`. The macOS updater defers while workers or Desktop turns are busy, so a saturated host can stay behind for hours. Keep manual containment (repins, re-assigns) running until the readback passes.

## Sign-in blockers (hub-session-sync sites)

1. Check: `/usr/bin/python3 ~/.hermes/hub-session-sync/hub_session_sync.py check <site>` (use the interpreter that has PyYAML; exit 0 = signed in).
2. The hub agent browser (`browser_exec`) already holds his Google sessions. Open the site's login page and choose "Sign in with Google". In the account chooser, click the row with JS: `document.querySelector('[data-identifier="<email>"]').click()`, or walk text nodes to that row's `role=link` ancestor. Coordinate clicks often miss there. The browser is shared with other sessions, so open your own tab with `new_tab` and re-read `location.href` before each step.
3. Verify it is HIS existing account (an existing plan, usage or billing history), not a freshly created one. If it is new, sign out and try the other address.
4. Re-run `check`, then `hub_session_sync.py resolve <site>`; the blocked card completes itself. Read its status back.
5. GitHub's OAuth "Authorize" button stays disabled for automated input. That is an anti-clickjacking guard, so never remove the `disabled` attribute; use a different SSO provider instead.
6. `run_in_user_terminal` only runs from the owner's own chat. From a dispatch session, do the hub-side route above rather than handing him a command to paste.
