# Kanban capacity evidence and execution observations v1

Patches: **2485–2491**.

## Behavior
Card reads gain advisory, versioned (v1) evidence that explains why a ready card is not running while worker capacity looks unused. It is shown by `kanban_show`, `hermes kanban show` and the dashboard task-detail REST route as optional siblings of the legacy `queue` fields:

- `capacity_evidence`: `freshness` (`current`/`stale`/`unknown`), `reasons[]`, `native_restrictions[]`, `machine_reasons[]`, `lifecycle`, `eligible_backlog`, `admissible_slots`, `unknown_coverage`, plus source identity (`source`, `source_revision`, `machine`, `board`, `evidence_ref`, `observed_at_ms`, `valid_until_ms`).
- `execution_observations[]`: an optional envelope (`docs/execution-observations-v1.md`) holding at most one adapted observation.
- `capacity_note` (JSON) / a `capacity:` line (CLI text): a one-line description, always ending in "admissible capacity unknown".

Reasons are concurrent, namespaced diagnostics, each with `code`, `native_code`, `phase` (`pre_claim`, `post_claim`, `post_start`) and `evidence_ref`: `capacity.memory_pressure`, `capacity.provider_limit`, `capacity.placement`, `capacity.dependency`, `capacity.update_drain`. Unmapped native admission restrictions (`at_capacity`, `claim_deferred`, `capsule_refused`, `owner_down`, `skipped_per_profile_capped`, `respawn_guarded`) stay visible beside them rather than being forced into a category.

Unknown, stale, foreign-board, truncated or lifecycle-changed evidence is reported as unknown/stale, never as free capacity, success or failure. Admission is unchanged: nothing here is read by scheduling.

Receipt metrics (library only, not yet surfaced anywhere) measure ready→claim→process-start from durable events. Unexplained idle slot-seconds are produced only for fresh, aligned, complete coverage with eligible backlog and admissible slots.

## How it works
- **Write seam.** `dispatch_once` in `hermes_cli/kanban_db_dispatch.py` runs `_dispatch_once_locked`, then calls `observe_dispatch` in `hermes_cli/kanban_capacity_evidence.py` and returns the same `DispatchResult`. `observe_dispatch` swallows every exception; `record` skips dry runs and `skipped_locked`/`skipped_owned` ticks and swallows `sqlite3.Error`, `RuntimeError`, `TypeError` and `ValueError`. The board comes from the actual connection (pinned DBs included), not the `board` argument.
- **Snapshot.** `record` reads up to `TASK_LIMIT` (128) cards in `ready/todo/running/review/scheduled/blocked` inside a `SAVEPOINT` (no writer lock held), maps `DispatchResult` fields to reasons, then upserts one bounded row in a lazily created `kanban_capacity_observation` table (single latest snapshot per board, TTL 180 s). More than 128 cards sets `coverage_truncated`. Machine-wide reasons (`memory_pressure`, and `update_drain` when requested) are attached only to ready, unclaimed, dependency-free cards. Cards with unsatisfied parents get `capacity.dependency` instead and are not eligible backlog.
- **Provider limits.** Only explicit quota clocks (`subscription_quota_reset`, `rate_limit_cooldown`) and a reaped `rate_limited` result map to `capacity.provider_limit`. A reaped result is `post_claim` unless `_provider_phase` finds the refusal event's own run with a matching `worker_bound` receipt, then `post_start`.
- **Update drain.** The gateway dispatcher (`gateway/kanban_watchers_dispatcher.py`) passes `observation_update_drain=True` to `dispatch_once` only when it suppresses spawns; this is a diagnostic flag, never an admission input. Existing hold behavior: [kanban-dispatch-update-hold-2253.md](kanban-dispatch-update-hold-2253.md).
- **Read.** `kanban_queue_position.detail_fields` composes the legacy `queue` fields with `capacity_evidence.read`, `execution_observations` and `capacity_note`; failures degrade to unknown. `read` never writes or renews validity. It returns unknown (`missing_or_foreign_observation`, `task_not_observed`, `task_coverage_truncated`, `lifecycle_changed`, `observation_unavailable`) when the board differs or the snapshot doesn't cover the card. A change to status, run, `runs_on`, assignee, run count or parent state invalidates the stored lifecycle. Patch 2486 added this source-identity/lifecycle fencing and stricter attempt-identity checks. Related legacy queue read: [kanban-ready-card-queue-reads-2131.md](kanban-ready-card-queue-reads-2131.md).
- **Envelope adapter.** `hermes_cli/execution_observations.py` `adapt` copies a v1 observation and bounds its validity: sidebar TTL 180 s, imported-owner TTL 600 s, each required source keeping its own shorter TTL. Missing identity, owner, evidence refs, timing or clock skew yields unknown; expiry yields stale with `last_known_state` kept. Legacy/unversioned input becomes unknown (`legacy_or_unsupported_version`) with no fabricated timestamps. Fetch time and file mtime never renew validity. Unclaimed ready/todo cards are reported `queued`/`waiting`; any other status is `unknown`.
- **Metrics.** `hermes_cli/kanban_capacity_metrics.py`: `attempts` walks ordered task events (producer order, not re-sorted). Readiness needs an explicit transition (`promoted`, `promoted_manual`, `unblocked`, `triage_swept`, or a retry event with `retry_status == "ready"`); creation time is never substituted. Events that leave ready (blocked, status changes, escalations, `imported`, etc.) discard an earlier ready receipt. Process start is the `worker_bound` event matching run, claim lock and pid; latency is a one-second-resolution receipt delta, not exact launch time. `summarize` keeps samples and censored counts (p50 needs 2 samples, p95 needs 20). `idle_coverage` unions shared slot-pool intervals across boards; unexplained idle is capped at `min(eligible_backlog, admissible_slots)` (patch 2488), disagreeing backlog or slot counts become unknown seconds, and unknown coverage is machine-seconds, not invented slots. Patches 2488 and 2489 add manual-ready, unblock, triage-sweep and import handling.
- **Entry paths.** `tools/kanban_show.py` calls `kqp.detail_fields` only on the live branch (`replica=False`); the replica branch uses an empty `details` and is unchanged. `hermes_cli/kanban.py` `_cmd_show` and `plugins/kanban/dashboard/plugin_api.py` `get_task` (live branch) use the same function. Patch 2485 changed `tools/kanban_show.py` by six lines for this.
- **Refactor (2491).** `_looks_like_path` and `_is_windows_batch_shim` moved unchanged into `hermes_cli/kanban_dispatch_paths.py` and are re-imported by `kanban_db_dispatch.py`, to keep that module within its size budget.

## Gotchas
- The source docs describe this as an implementation checkpoint, not delivery: final review, extra lifecycle coverage, CI, publication and live readback were outstanding.
- `admissible_slots` is always null in current snapshots (configured limits are not measured free slots), so the metrics' unexplained-idle figure cannot be produced from dispatch snapshots alone; `eligible_backlog` is only ever `false` (dependency-held) or null.
- The local dispatcher's `update_drain` reason is attached to every ready, unclaimed, dependency-free card on the board, including cards pinned to another machine. The evidence names the local gateway as `machine` in `evidence_ref` and `machine_reasons`, so read it as "this dispatcher was draining", not "the card's pinned machine was".
- Only the latest dispatch tick is stored (one row per board); a later tick overwrites it, and snapshots expire after 180 s.
- Receipt latency uses `worker_bound`, not submitter `spawned`, events; resolution is one second.
- Replica (foreign) cards deliberately get no capacity fields: a replica cannot describe this gateway's capacity.
